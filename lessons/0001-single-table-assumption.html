The Single-Table Assumption

Lesson 001 · Phase 1 · ~40 min

Your contrarian bet targets relational deep learning — but almost every tabular library, Kaggle notebook, and production pipeline starts from the same hidden contract: one row = one training example, columns = features. Before RDL can win, you need to see exactly what that contract costs.

What tabular ML actually eats

scikit-learn, XGBoost, and neural tabular models expect a matrix X and a vector y. Real companies store data in many linked tables — customers, orders, products, sessions. Someone must join, aggregate, and featurize those tables into one flat file. That work is feature engineering.

The contract is strict: row i of X must align with label y[i]. The learner receives feature values, not the original tables and joins. Numeric or categorical identifiers can be included as features, but their presence does not automatically tell the model which rows are linked. Every relational ML project therefore has two systems: the database (recorded observations) and the design matrix (what the model sees). Lesson 002 makes that second system precise.

Fey et al. (ICML 2024): feature engineering on relational data is argued to be costly and vulnerable to mistakes. The paper proposes learning over connected tables instead. This is a research proposal, not proof that every graph model outperforms a well-engineered flat-table model.

Worked example: e-commerce churn

Imagine a subscription retailer. The warehouse holds at least four tables: 

customers(customer_id, signup_date, country, plan_tier)
orders(order_id, customer_id, order_date, amount, category)
sessions(session_id, customer_id, start_time, pages_viewed)
support_tickets(ticket_id, customer_id, opened_at, resolved_at, topic)

The business question: will customer c cancel in the next 30 days? First define the prediction cutoff t. A primary key uniquely identifies a row; a foreign key points to a row in another table. Several orders can point to the same customer, so joining child tables can multiply rows. Aggregate each child table to one row per customer before joining its features: 

WITH order_features AS (
  SELECT customer_id, COUNT(*) AS order_count_90d
  FROM orders
  WHERE order_date > date(:cutoff, '-90 days')
    AND order_date <= :cutoff
  GROUP BY customer_id
), session_features AS (
  SELECT customer_id, AVG(pages_viewed) AS avg_pages
  FROM sessions
  WHERE start_time <= :cutoff
  GROUP BY customer_id
), ticket_features AS (
  SELECT customer_id, COUNT(*) AS ticket_count
  FROM support_tickets
  WHERE opened_at <= :cutoff
  GROUP BY customer_id
)
SELECT c.customer_id,
       CAST(julianday(:cutoff) - julianday(c.signup_date)
            AS INTEGER) AS tenure,
       COALESCE(o.order_count_90d, 0) AS order_count_90d,
       s.avg_pages,
       COALESCE(t.ticket_count, 0) AS ticket_count
FROM customers AS c
LEFT JOIN order_features AS o USING (customer_id)
LEFT JOIN session_features AS s USING (customer_id)
LEFT JOIN ticket_features AS t USING (customer_id)
WHERE c.signup_date <= :cutoff;

Read the SQL. Each WITH clause names an intermediate table. GROUP BY returns one row per customer in that table. LEFT JOIN retains customers with no history; COALESCE(...,0) makes their counts zero. A missing session average stays NULL: no sessions is not the same observation as zero pages. This is executable SQLite syntax with ISO date strings and a bound :cutoff. It assumes events were available when they occurred and customer attributes were not retrospectively overwritten. Lesson 2 separates those assumptions from timestamp filtering.

Trace the row multiplication before trusting a count

Customer 1 has two orders (amounts 20 and 30), two sessions (4 and 8 pages), and one ticket, all before the cutoff. Joining all three raw child tables makes 2 × 2 × 1 = 4 rows:

A raw-join COUNT(order_id) returns 4, and so does COUNT(ticket_id). Pre-aggregation gives order_count_90d=2, avg_pages=6, ticket_count=1, matching the diagram below. The average happens to survive this balanced multiplication; the counts do not. A future order must affect neither count. An eligible customer with no child rows must still produce one feature row, with counts zero and average NULL.

Notice what happened. Four tables became one row per eligible customer at this cutoff. The customer key remains for joining labels and auditing rows, but need not be a model input. The graph of “who bought what, when, and after which session” collapsed into four hand-picked aggregates. That collapse is not neutral — it is a modeling choice baked into SQL that the gradient booster will never question.

Three ways the assumption breaks

  1. Lost structure. Primary–foreign key links encode who bought what, who knows whom, which event belongs to which user. Flattening collapses that graph into hand-picked aggregates (count_orders_30d, avg_session_length). Neighbors in the graph — products co-purchased, users in the same household — never appear unless someone engineers them.
  2. Leakage risk. A careless join can smuggle future information into features. Temporal relational data needs explicit availability rules and time-respecting splits. A relational entity graph does not establish historical availability by itself. A feature that sums all orders, not just orders before the prediction date, can look predictive while cheating.
  3. Suboptimal signal. RelBench’s user study found GNNs on the full relational graph matched or beat an experienced data scientist’s manual features while cutting human effort by an order of magnitude (Robinson et al., NeurIPS 2024). This is evidence from the paper’s particular tasks and user-study protocol, not a guarantee of the same accuracy or labor savings on another database.

What relational deep learning proposes

RDL keeps the database shape. Fey et al. introduce a relational entity graph (REG): tables become node types, rows become nodes, foreign keys become edges. Message-passing neural networks (Year 3) can then learn over that graph instead of over a pre-flattened CSV.

This does not eliminate feature engineering overnight. You still need temporal splits, point-in-time labels, and honest baselines. Phase 1 exists so you can say, with evidence: “I beat a strong flat-table XGBoost on the same prediction task before I claim the graph helped.”

Common objections (and honest answers)

“We already ETL into a feature store — isn’t that enough?”
Feature stores version and serve aggregates; they do not remove the single-table contract. They industrialize the flattening. RDL asks whether the flattening step should be learned rather than hand-specified.
“Graphs are slow and hard to deploy.”
True for naive implementations. That is an engineering problem, not a reason to ignore lost structure. Your thesis lives at the frontier where graph models start winning on real benchmarks — RelBench, ContextGNN, RelGT — not in toy demos.
“GBDTs already win Kaggle tabular.”
Tree ensembles are strong single-table baselines, but there is no universal winner. Grinsztajn et al. compare methods under their declared tabular protocol; that is not evidence about temporal deployment. Later lessons distinguish random-split benchmarks from temporal evaluation. Whether relational models add useful signal must be tested with the same eligible information, population and selection budget.
