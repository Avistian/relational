Document a Baseline Package

Lesson 037 · Phase 1 · Q4 · ~55 min · primary reading: Pineau et al., JMLR 22(164), 2021

L036 ended with three fixes owed to a pipeline that had just been audited: a person-grouped inner calibration split, in-fold preprocessing, and shipping M1 rather than M2a. Every one of those is a change you would have to re-measure to believe. And the moment you say that out loud, a prior question appears that the whole audit quietly assumed: when you run that pipeline again tomorrow, do you get the same number back?

Most people answer yes without checking, on the strength of a sentence like the one in the submission's own README — "All randomness is seeded." That sentence is true. This lesson measures what it actually buys, on the same pipeline, and the answer is: on one reading, nothing at all, because the seed it refers to is never consulted. On another reading, it is the largest controllable term in the entire report. Both readings use the same variable.

Its single skill: turn an audited pipeline into a package that regenerates its own headline number on command and fails loudly when it cannot — which means pinning the things that measurably move the number rather than the things folklore says do, naming the number precisely enough that two people compute the same one, and choosing a tolerance you could have justified before you saw the answer.

One sentence. A baseline package is not a description of a result — it is a machine that reproduces the result and refuses when it can't, and building one forces three things into the open that prose lets you leave vague: which inputs the number actually depends on, which estimator the number actually is, and how far it may move before you should stop believing it.

Warm up — recall before you read

Three questions from earlier lessons, from memory, before today's material. A failed retrieval still encodes better than a re-read.

First, the vocabulary (nothing here is assumed)

"Reproducible" is one of those words everyone uses and nobody defines, which is exactly how two people end up satisfied by different things. Everything this lesson relies on is defined here from first principles.

Artifact. In the reproducibility literature this is a term of art, not a synonym for "model file." An artifact is any digital object created to run the study or produced by it: the source code, the scripts that launch the experiments, the input data, the raw outputs, and the analysis scripts that turn outputs into the tables in your report (ACM Artifact Review and Badging v1.1). "Package your pipeline" means: assemble those objects so that someone else can run them.
Repeatability, reproducibility, replicability. Three rungs, distinguished by who runs it and with what. Repeatability = same team, same setup: you can re-run your own computation and get your own answer. Reproducibility = different team, same setup: an independent group gets your result using your artifacts. Replicability = different team, different setup: an independent group gets your result from artifacts they wrote themselves. A warning worth carrying: ACM swapped the definitions of "reproduced" and "replicated" in May 2020 to match the wider scientific community, so any paper older than that may use them the other way round. When it matters, say "same artifacts" or "independent artifacts" and skip the noun.
Determinism, and bitwise vs. statistical reproduction. A computation is deterministic if the same inputs always produce the same outputs, down to the last bit. Bitwise reproduction means the new output is byte-for-byte identical to the old one — you can check it with a hash and there is nothing to argue about. Statistical reproduction means the new number is close enough to the old one, which requires you to have said, in advance, what "close enough" is. Bitwise is a much stronger claim, and — this is the surprise of the lesson — it is often available for free on CPU tabular pipelines, so it is worth checking before settling for the weaker one.
Fingerprint (content hash). A short digest of a large object, such that any change to the object changes the digest. Here: run SHA-256 over the raw bytes of the out-of-fold probability matrix and keep the first 16 hex characters. Two runs producing d2f0e4bf9b4fd761 agree on all 27,935 predicted probabilities; two runs producing different digests disagree somewhere, and the digest does not tell you where — you still need the max |Δp| and the count of flipped predictions for that. The hash is the alarm, not the diagnosis.
Constraint, pin, and lockfile. A constraint such as lightgbm>=4.0 says which versions you will tolerate; it is a statement about the future. A pin such as lightgbm==4.6.0 says which version you want. A lockfile (uv.lock, poetry.lock, pip freeze output) records the version and content hash of every package that was actually installed, transitive dependencies included, so the environment can be rebuilt exactly. Only the third of these describes what you ran. The submission has one; this workspace, as we will see, does not.
Entry point. One named command that runs the whole thing — make baseline, python -m hw.run baseline, uv run hw-baseline. Its defining property is that there is no correct order for the reader to get wrong. Three notebooks that must be executed 01 → 02 → 03 is not an entry point; it is an ordering constraint expressed in English, and English does not raise exceptions.
Run manifest. A machine-written record, emitted by the run, of everything needed to interpret its output: the git commit, whether the working tree was dirty, the resolved versions of every dependency, a content hash of the input data, every seed, the thread count, the machine, the wall time, and the numbers produced. Its purpose is to make the question "was this the same experiment?" answerable months later without relying on memory.
Estimator of record. The exact recipe by which a metric is turned into a single number — not just log-loss or ECE, but "mean over the five outer folds of the per-fold value" or "one value computed over all pooled out-of-fold rows at once." Two estimators of the same metric on the same predictions can disagree substantially, and neither is wrong. §"Name the number" below is entirely about this.
Noise floor of an estimator. The value your estimator reports for a model that is perfect on the thing being measured. For a mean it is zero. For a binned statistic like ECE it is emphatically not: bin a small sample and you will observe gaps between confidence and accuracy that are pure sampling noise, and because ECE sums absolute gaps, that noise cannot cancel — it accumulates. Any reported value below its own noise floor is a measurement of the ruler.
Tolerance. The threshold in a reproduction check: fail unless |new − expected| ≤ tol. A tolerance chosen after seeing the new number is not a test, it is a rationalisation, so tol belongs in the config file next to the expected value.
Configuration debt. Sculley et al.'s name (in Hidden Technical Debt in Machine Learning Systems, NeurIPS 2015, §6) for the observation that mature ML systems accumulate enormous configuration surfaces — every feature, every threshold, every seed, every sampling rule — which are typically treated as an afterthought, are rarely reviewed, and are where a surprising share of production errors live. Their prescription is that configuration should be a first-class, reviewable, diff-able artifact. It is the difference between a number scattered across four notebook cells and a number appearing once in a file.

What it is missing is not hygiene but a gate: nothing anywhere in the repository would notice if a rerun produced a different answer. The rest of this lesson builds that gate, and in the course of building it discovers which inputs the number actually depends on — which turns out not to be the list you would guess.

Read the experiments in the right units. Everything measured below runs the uncalibrated LightGBM arm — the same 400-tree model, the same person-grouped 5-fold splitter, the same encoded matrix, but without the isotonic wrapper. That is deliberate: CalibratedClassifierCV takes five inner splits of its own, so leaving it in would mean each "run" contained six models and any difference could be blamed on the calibrator. The cost is that the absolute level is 1.6322 rather than L036's calibrated 1.4248, and one fold's standard deviation is 0.0350 rather than 0.0392. When a delta measured here is compared to the 0.0032 margin from L036, treat it as a comparison of magnitudes in the same units on the same data, not as a like-for-like difference of two numbers from one table.

Nine ways to break it — and the eight that didn't

The standard advice about ML reproducibility is a list of hazards: set your seeds, pin your threads, beware floating-point non-associativity, distrust GPU reductions. It is good advice and it is generic, which means it tells you what to worry about but never what is actually true of the code in front of you. So rather than repeat the list, we ran it.

The design is a paired perturbation study, and it is worth stating in the L036 style before the numbers appear. Held fixed: the data, the joined feature frame, the encoder, the outer person-grouped 5-fold splits, the model hyper-parameters, the metric code, and the machine. Varied: exactly one knob per configuration. Measured: the full out-of-fold probability matrix, 5,587 × 5 float64 values, hashed with SHA-256, plus the mean per-fold log-loss and — where the hash differs — the largest single-probability change and the number of rows whose predicted class flipped. This isolates the knob because a hash mismatch cannot come from anywhere else: nothing but the knob was allowed to move.

The eight that didn't move: what a negative result is worth

Eight perturbations, one hash. Thread count from 1 to 12 — the knob that L036 turned to make the audit affordable — changes only wall time. LightGBM's own deterministic flag, documented as ensuring "stable results when using the same data and the same parameters (and different num_threads)", has nothing to stabilise. Forcing the histogram construction row-wise or column-wise — the choice LightGBM otherwise makes by timing both on your machine at fit time, and therefore in principle a dependence on how busy the box was — makes no difference to the model. Shuffling the training rows makes no difference either, because LightGBM buckets each feature into at most 255 bins before summing anything, and a bin's total does not care in what order its members arrived.

It would be easy to read that as "the warnings were overblown, skip the pins." That is exactly the wrong conclusion, for a reason worth being precise about. The value of these eight runs is not that they let you remove anything; it is that they let you say something. Before, you had a README sentence expressing a hope. Now you have a measurement: on this data, this model and this machine, the result is bit-stable under every threading and ordering perturbation available, and one line in the run manifest — n_jobs — can be varied by whoever reproduces you without invalidating the comparison. That is a real permission, it is only granted by evidence, and it cost about eleven minutes of CPU.

The permission is also strictly local. It holds for CPU histogram gradient boosting on 5,587 rows. It will not survive contact with Year 2: a GPU reduction sums partial results in whatever order the blocks finish, cuDNN picks algorithms by benchmarking, and PyTorch's own reproducibility notes open by saying that completely reproducible results are not guaranteed across releases, platforms, or even between CPU and GPU on one machine. The habit to build is not "threads are safe"; it is "measure whether threads are safe here, and write down the answer."

The one that moved: a cast nobody documented

Consequence class · degrades the artifact for individual people; the aggregate barely notices

.astype(np.float32) — in a notebook cell, in neither the README nor src/

# notebooks/02_task2_modeling.ipynb, cell 3
X_all = pipe.fit_transform(X_df).astype(np.float32)   # halve the memory, and...?

Drop that cast — change nothing else, not the seed, not the folds, not a hyper-parameter — and the out-of-fold matrix is a different object. The mechanism is not mysterious. LightGBM does not split on raw feature values; it first bins each feature into at most 255 buckets and searches only over bin boundaries. A value stored as float32 carries about 7 decimal digits; the same value in float64 carries about 16. For the overwhelming majority of rows the two land in the same bucket and nothing happens. For a few, near a boundary, they do not — and once one split threshold moves, every tree grown after it in the boosted sequence is grown on different residuals, so the divergence compounds.

What it costs depends entirely on which question you ask, and the two answers point in opposite directions:

QuestionAnswerRead against
How much did the reported number move?Δ mean log-loss +0.00133 3.8 % of one fold's σ (0.0350) — invisible
How many folds even changed?2 of 5 (folds 2 and 3) folds 0, 1 and 4 are bit-identical
How far did a single prediction move?max |Δp| = 0.326 a probability of 0.60 becoming 0.27
How many people got a different predicted outcome? 258 of 5,587 — 4.6 % every one of them a real person in an EU-facing HR system

This is the L036 consequence-class distinction reappearing in a new place, and it is the reason that lesson came first. A defect can be invisible to the number and severe in the artifact. The mean is an average over 5,587 rows and it absorbs 258 flips without flinching; the 258 individuals do not have the luxury of being averaged. If your report says "the model recommends X for this person," and an undocumented dtype cast decides that for 4.6 % of them, then the cast is part of the model — and it belongs in the config file, under review, next to the learning rate, rather than in a notebook cell that exists to save memory.

Put next to the other measurement we have on this data: the margin by which M2a was chosen over M1 — the difference that decided which artifact went to production — was 0.0032 nats. The dtype cast is worth 0.00133, about 42 % of it. (Different arm, same data and units; read it as an order of magnitude, not a subtraction.) A deployment decision made on a margin that undocumented representation choices can supply half of was not, in any useful sense, a decision about the models.

The one that didn't run at all

Consequence class · the reproduction fails closed — the good outcome, and the reason to prefer it

lightgbm 4.5.0 with scikit-learn 1.9.0: TypeError

TypeError: check_X_y() got an unexpected keyword argument 'force_all_finite'

The experiment: build a second virtual environment pinning identical versions of numpy, pandas, scipy, scikit-learn, pyarrow, joblib and threadpoolctl, changing only lightgbm==4.6.0 to 4.5.0, and run the reference configuration. It never reaches a number. scikit-learn renamed force_all_finite to ensure_all_finite in version 1.6 and deleted the old name in 1.8; LightGBM 4.5.0 still calls it.

Two things follow, and the second is the one that changes how you write a dependency file.

First: an environment drift does not politely present as a slightly different number. Its most common presentation is a crash, and a crash is the merciful case, because you cannot mistake it for a result. The dangerous version of this same event is a library that silently changes a default — and you only know which kind you got if something regenerates the number and compares it.

Second, and this is close to home: both of those versions satisfy this workspace's own requirements-labs.txt, which asks for lightgbm>=4.0 and scikit-learn>=1.5 and ships no lockfile at all. A constraint is a statement about which futures you are willing to accept, and it accepts far more of them than you think — including futures in which two individually valid packages cannot be installed together. Every verified number in every learning record in this workspace was produced by a specific resolution of those constraints that is currently written down nowhere. That is today's most actionable finding, and the lab fixes it.

Name the number

Suppose the environment is nailed down and the fingerprint matches. There is still a way for two honest people to disagree about whether a result reproduced, and it has nothing to do with computers. It is that "the ECE" is not one number.

Here is the same shipped model (M2a), the same saved out-of-fold predictions, the same metric name, in two places in the same repository:

DocumentSaysEstimator actually used
report.md §3.1 — the model-selection tableECE 0.0332 ± 0.0100 compute ECE inside each of the 5 outer folds (n ≈ 1,117), then average
README.md headline and report.md §4 ship-gate table ECE 0.018 pool all 5,587 out-of-fold rows and compute ECE once

Recomputed from the saved artifact: 0.017760 pooled against 0.033200 averaged over folds. Neither is a mistake, neither is a leak, and the gap is a factor of 1.87. Note also which is which: the model was selected using the larger estimator and ship-gated using the smaller one.

Before explaining it, rule out the obvious suspect. Does pooling versus averaging always disagree? No — on the same predictions, log-loss comes out at 1.4215533 pooled and 1.4215443 averaged, agreeing to five decimals. Log-loss is a plain mean of one term per row, so averaging five near-equal-sized means of it recovers almost exactly the mean of all of them; the two operations commute. ECE is not a mean of per-row terms. It is

ECE = Σb (|Bb| / N) · | accuracy(Bb) − confidence(Bb) |

— a weighted sum over bins of the absolute gap between how often the model was right in that bin and how confident it was. Two features of that formula do the damage. Binning depends on how many rows you have: cut the sample into five and every bin has a fifth as many rows, so each bin's accuracy is estimated from a fifth as much evidence and is correspondingly noisier. And the absolute value means that noise cannot cancel: a bin that happens to run 5 points hot and a bin that happens to run 5 points cold both contribute +0.05, where in a signed average they would have annihilated. Sparser bins therefore do not merely make ECE noisier — they make it systematically larger.

You can watch it happen. Below, the same predictions binned two ways; the red bars are bins holding fewer than 25 rows.

Look at the rightmost bar in each view. Pooled, the top populated bin holds 17 rows and shows a gap of 0.19. In fold 0 that same region of confidence holds 2 rows — one predicted correctly, one not — and shows a gap of 0.40, a number produced entirely by the arithmetic of ½ against a confidence of 0.90.

How much of the 0.0332 is real?

"Systematically larger" is a mechanism, not a size, so measure it. Two experiments, both on the saved predictions, both in labs/_ece_estimator_l037.py.

Experiment one — is it the folds, or just the sample size? Take the pooled matrix and cut it into five random blocks of 1,117 rows — no person grouping, no fold structure, nothing but the size — and average their ECEs. Repeat 500 times. Result: 0.03432 ± 0.00336, with a 90 % interval of [0.0289, 0.0402]. The real per-fold mean of 0.0332 sits comfortably inside that. Whatever the five folds are doing, it is not distinguishable from what five arbitrary blocks of the same size do.

Experiment two — what would a perfect model score? Build a control with true ECE exactly zero by construction: take the model's own probability vector for each row and resample the label from it. Now the model is, by definition, perfectly calibrated. Run the identical estimator, at each sample size, 300 times:

The consequences for the submission are three, in increasing order of seriousness.

The §3.1 selection number is almost all ruler. At fold size the estimator reports 0.0335 for a perfect model and 0.0344 for this one. The models in that table were compared, in part, on a quantity whose informative content is roughly 0.001 out of 0.033.

The README's 0.018 is the better number, and should say so. Pooled, the floor is 0.0149 and the model reads 0.0178 — a signal of about 0.003, small but real, and about three times better resolved than the per-fold version. The right fix is not to pick a favourite but to name it: "top-label ECE, 15 equal-width bins, computed once over all 5,587 pooled out-of-fold rows."

The one gate the submission failed cannot be passed by anything. §4.7 records a CONDITIONAL verdict, failing the slice gate on the 107-row age = missing cell at ECE 0.094 against a threshold of 0.05. At n = 107 this estimator reports 0.1071 ± 0.0297 for a model that is calibrated exactly right. The observed 0.094 is below the noise floor. There may well be a real calibration problem in that slice — but this measurement cannot see it, and the gate as written would fail a perfect model. A ship-gate whose threshold sits under its own estimator's noise floor is not a safety check; it is a coin flip with a procedure attached.

There is a counter-intuitive corollary, and the lab makes you predict it before it shows you. Strip the isotonic step out of this pipeline and the resulting model is genuinely badly calibrated — pooled ECE around 0.093, roughly eight times its own floor. On that model the two estimators agree to within 1 %, because a large real miscalibration swamps the bias. The estimator you pick matters least when the number is bad, and most when it is good. Which is to say: it matters precisely when you are about to ship, and precisely when you would most like to believe the smaller of the two figures in front of you.

What this has to do with packaging. Everything, and it is the point of the section. The reason the same repository contains 0.0332 and 0.018 is that no single place defines the number. A run manifest that emits {"metric": "ece_top", "bins": 15, "estimator": "pooled_oof", "n": 5587, "value": 0.01776} makes the two impossible to confuse, makes the ship-gate's threshold reviewable against the estimator it is applied to, and makes a reproduction check meaningful — because you cannot compare two numbers until you know they are the same number.

Which seed?

src/modeling.py defines RANDOM_STATE = 0 once and hands the same integer to the estimator and to the splitter. The README summarises this as "all randomness is seeded." Both statements are correct, and they conceal a factor-of-infinity difference in importance.

The model seed · inert

Seeds 0, 1, 2, 3, 4 produce one identical hash

LightGBM consults its random number generator only when it samples: row subsampling (bagging_fraction < 1), column subsampling (feature_fraction < 1), or randomised split thresholds (extra_trees). This configuration sets none of the three, so the RNG is never asked for a number and the seed cannot matter. Setting it was harmless and reasonable; believing it bought reproducibility was not.

Nothing about the model changed across those five runs. The same 400 trees, the same hyper-parameters, the same encoded matrix. All that changed is which persons landed in which fold, and the reported headline moved over a range of 0.0166 nats — five times the margin that decided which model shipped, twelve times the dtype effect, and about half of one fold's own standard deviation.

Three things follow. Reporting a single fold draw is reporting a sample of one from a distribution with a visible spread; L023's answer to this is repeated cross-validation (5×5), and this is what that recommendation costs and buys. The splitter seed is load-bearing config and belongs in the manifest by name, not folded into a variable called RANDOM_STATE that also feeds three things where it does nothing. And "seeded" is not a property, it is a question: seeded where, consulted by what, and with what consequence if it changes? Probing each seed independently is a ten-minute experiment that turns a slogan into two facts.

Choosing the tolerance

Now the gate itself. The check is |new − expected| ≤ tol, and everything hinges on tol, because the measured landmarks on this pipeline span four orders of magnitude. Slide it and read what each choice buys.

The reasoning behind the recommended setting runs as follows. Start from the strongest claim the evidence supports. Eight of nine perturbations were bitwise identical, which means a hash equality check — tolerance zero — will not produce false alarms on this pipeline, so that is the default gate, and it has the enormous practical advantage of needing no threshold at all. Fall back only when you must, and say why. When a genuinely stochastic component enters (a GPU reduction, an early-stopping split, torch), bitwise becomes unachievable and you switch to a numeric tolerance — at which point the tolerance must be derived from a measurement, not chosen for looking reasonable. Bound it from below and above. Below: it must exceed the drift you have measured and accepted, or it fires on nothing but itself. Above: it must stay well under the smallest difference you intend to make a decision on — and on this pipeline that is 0.0032 nats, which rules out anything approaching the fold σ.

The tolerance trap. The failure mode is not choosing badly, it is choosing afterwards. You run the reproduction, get 1.6335 against an expected 1.6322, and set tol = 0.002 so the test passes. That gate has no power: it was fitted to the observation it was supposed to judge. The discipline is the same one L023 taught for p-values and L017 for model selection — the threshold is part of the protocol, so it is written down before the number that will be compared against it, and it lives in the config file where a reviewer can see it.

The config file is the interesting part

Sculley et al.'s configuration-debt argument says the configuration surface of an ML system is large, under-reviewed, and disproportionately responsible for errors. This lesson found two concrete instances on one pipeline: a .astype(np.float32) that changes 258 predictions and lives in a notebook cell, and a RANDOM_STATE that means two unrelated things in two places. Both are configuration masquerading as code. Pulling them into one reviewable file is the fix: 

# baseline.yaml — every knob this lesson measured, in one diffable place
data:
  source: data/          # persons|situations|responses .parquet

split:
  kind: stratified_group_kfold
  n_splits: 5
  group: person_id
  seed: 0               # MEASURED: seeds 0-4 span 0.0166 nats. Load-bearing.

  n_estimators: 400
  learning_rate: 0.05
  num_leaves: 31
  min_child_samples: 50
  reg_lambda: 1.0
  seed: 0               # MEASURED: inert (no bagging/feature sampling). Kept for the day it isn't.
  n_jobs: 6             # MEASURED: no effect on output; 3.5 s/fit vs 9.8 at 1 and 13.7 at 12

    metric: log_loss
    estimator: mean_over_outer_folds

  calibration:
    metric: ece_top
    estimator: pooled_oof   # NOT mean_over_folds: at n=1117 the noise floor is 0.0335
    bins: 15
    expected: 0.017760
    tol: 0.0

Read the comments. Each one is a measurement from this lesson, and each answers the question a reviewer would otherwise have to ask. That is what distinguishes a config file from a pile of constants: the constants are the same, but the file records why each value is the value and what happens if it changes. Note also what the estimator: keys have accomplished — the 0.0332/0.018 ambiguity is now unrepresentable, because there is nowhere to write "the ECE" without also writing how it is computed.

The manifest, and the check it enables

The manifest is written by the run, not by you, which is the whole point: a hand-maintained record of what you ran is a record of what you meant to run. 

# artifacts/run_manifest.json — emitted by every `make baseline`
{
  "git_sha": "8518888", "git_dirty": false,
  "data_sha256": "3f9c…",        # hash the inputs: a silent data swap is otherwise invisible
  "config_sha256": "b1e0…",      # hash baseline.yaml: proves which knobs were in force
  "env": {"python": "3.12.6", "lightgbm": "4.6.0", "scikit-learn": "1.9.0",
           "numpy": "2.5.0", "pandas": "3.0.3"},
  "host": {"platform": "Linux-6.6-WSL2", "machine": "x86_64", "cores": 12},
  "seeds": {"split": 0, "model": 0},
  "oof_sha256": "d2f0e4bf9b4fd761",   # the fingerprint the gate compares
  "results": {"log_loss_mean_over_folds": 1.632168, "ece_top_pooled_oof": 0.017760},
  "wall_seconds": 23.2
}

With that file, make verify is four lines of logic and answers a question no amount of prose can: re-run the entry point, compare the new manifest to the committed one field by field, and on any mismatch report which field moved. A changed env with an unchanged oof_sha256 is a dependency upgrade you have just proven safe. An unchanged env with a changed oof_sha256 is a bug you introduced. A changed data_sha256 that nobody announced is the worst news the file can carry, and the only mechanism you have for hearing it.

One deletion: nbconvert --execute --inplace

The submission's documented reproduction path runs three notebooks with nbconvert --to notebook --execute --inplace. Three problems, in ascending order.

The ordering is enforced by a sentence in the README — "run the three notebooks in order" — and running them out of order produces artifacts silently derived from a stale predecessor rather than an error. The --inplace flag then makes the notebook both the source and the output, so every run rewrites the file you are versioning and a git diff after a successful reproduction is a wall of changed execution counts and re-serialised base64 images. And most subtly: a notebook's state depends on execution history, not just on its contents, so a cell deleted after it ran still shapes everything downstream of it, and nothing in the saved file records that it was ever there.

The fix is not to abandon notebooks. It is to invert which one is authoritative: the logic moves into src/hw/ where it can be imported, tested and diffed, and the notebooks keep the narrative, the plots and the explanation, importing hw like any other consumer. They become an excellent way to read the pipeline and stop being the only way to run it.

Explain it back

This is the load-bearing idea — put it in your own words before moving on.

Thesis bridge. The mission's bet is that relational deep learning is undervalued, and the way that bet gets settled is a comparison: an RDL model against a tuned GBDT with manual feature engineering, on RelBench, with numbers a skeptic will attack. Everything in this lesson is a precondition for that comparison being worth running. The RelBench leaderboard gaps you will be trying to move in Years 3–4 are frequently a few percent; this lesson found an undocumented dtype cast worth 42 % of a shipping margin and a fold draw worth five times one. If your baseline cannot regenerate its own number, you cannot tell your improvement from your environment — and a reviewer who suspects that has no reason to read further. There is a sharper version too. The thesis's strongest claim is comparative, so it requires two reproducible pipelines, and the honest baseline is the one you are least motivated to package carefully. The discipline that makes the claim credible is packaging the GBDT baseline to exactly the standard you would demand of a paper that beat you.

Where this is subtle (know this too)

  • A negative result is a deliverable, not a wasted afternoon. Eight perturbations changed nothing, and that is a finding you can put in the manifest: whoever reproduces this may vary the thread count freely. Generic advice cannot grant that permission; only a measurement on this pipeline can. The eleven minutes bought a sentence you are entitled to say.
  • "Seeded" is a question, not a property. One RANDOM_STATE = 0 fed two consumers: one where the RNG is never consulted, and one that moves the headline by five times the shipping margin. Any claim about seeding that does not name the consumer is unfalsifiable — probe each seed separately and record what each is worth.
  • Aggregate stability is not individual stability. The dtype cast moved the mean log-loss by 3.8 % of one fold's σ and changed the predicted outcome for 258 people. Reproducing a table is a weaker check than reproducing an artifact, and in a deployment where individual predictions have consequences, it is the weaker check that most reports perform.
  • A metric name is not an estimator. "ECE 0.0332" and "ECE 0.018" are the same metric, the same model and the same predictions. Until the aggregation rule, the bin count and the sample size travel with the number, two people can reproduce each other's work exactly and still disagree about whether they did.
  • Check a threshold against its estimator's noise floor. A gate at ECE < 0.05 applied to a 107-row slice, where a perfect model scores 0.107 ± 0.030, cannot be passed. Before believing any small reported value, ask what the same procedure would report for a model that was exactly right — and if you cannot answer, build the control by resampling labels from the model's own probabilities.
  • Failing closed is the good outcome. The version rollback crashed rather than returning a subtly different number, and the crash is the merciful case. Every design choice here — the hash, the manifest comparison, the pre-registered tolerance — is an attempt to convert silent drift into loud failure, because silent drift is indistinguishable from a result.
  • Reproducible is not correct. A pipeline with a leak reproduces its leak perfectly. L036 asked whether the number is right; this lesson asks whether it is stable. Both are necessary and neither implies the other, which is why the audit came first and the package second.

Most map cleanly onto a file — hyper-parameter ranges and the selection method onto baseline.yaml, the computing infrastructure and the exact number of evaluation runs onto run_manifest.json, the central tendency and error bars onto RESULTS.md. Two short companions if you have the appetite.
