Change the examples and the inference procedure separately¶

Your goal is to build and distinguish three systems: a global pretrained PFN, the same PFN with a query-specific retrieved context, and a PFN adapted by gradients on local-context episodes. Read Thomas et al., Sections 2.2–2.4. Retrieval changes which labeled examples enter the forward pass. Fine-tuning changes neural parameters. One is not evidence that the other happened.

Nearby examples can help an irregular target because a limited context spends fewer slots on irrelevant regions. But locality can also discard useful distant structure, minority classes or rare exceptions. The paper evaluates retrieval and adaptation together and separately; the lesson keeps those ablations explicit rather than promising that nearest neighbors always improve a pretrained model.

Locality reallocates a finite context budget¶

An in-context learner can read only a finite set of labeled examples in one prediction call. A global context spends that budget on broad coverage. A local context spends it on rows close to the query under a chosen geometry. The benefit depends on whether that geometry concentrates examples relevant to the target relationship.

Locality can help when the useful decision rule varies across feature space or when distant examples consume slots without clarifying the query. It can hurt when distant rows establish a global trend, when rare classes disappear from the neighborhood or when irrelevant coordinates distort distance. These are testable hypotheses, not guarantees of nearest-neighbor retrieval.

There are three separate procedures in this lesson: a frozen global PFN, a frozen PFN with retrieved context and an adapted PFN evaluated with retrieved context. Comparing the first two isolates context selection under matched weights. Comparing the latter two examines adaptation under the declared local-context procedure.

The adapted model must start from a copy of the original checkpoint. Some APIs cache or share model objects. If fine-tuning mutates the object later used as the “frozen” baseline, the ablation has lost its control. Verify both parameter identity at initialization and separation after adaptation.

Retrieve in a declared geometry¶

Fit imputation and scaling on training rows. For query q and candidate row x, squared Euclidean distance is the sum of squared coordinate differences after that transformation. Without scaling, a large-unit feature can dominate the neighborhood for purely numerical reasons. Even standardized Euclidean distance is a modeling choice: it assigns equal weight to coordinates, assumes that numeric proximity is useful and can behave poorly with many irrelevant features.

Select the k smallest distances using a stable tie rule. During training episodes, exclude the query or anchor by original row identity. Excluding only distance zero would wrongly remove distinct duplicate rows; excluding only the first neighbor could retain the anchor under ties. At deployment, candidate labels must also be available at prediction time. Learned retrieval metrics require their own fit/validation boundary.

Distances encode a modeling assumption¶

Suppose a query has age 40 and income 50,000. Candidate A differs by 10 years and 100 currency units; candidate B differs by one year and 1,000 units. Raw squared Euclidean distance is dominated by income, favoring A despite its larger age difference. Training-fitted scaling can change the ordering by making coordinate units comparable.

Scaling does not discover relevance. Standardized Euclidean distance still weights coordinates according to a chosen rule, can struggle with many irrelevant features and may handle categorical encodings poorly. If a learned metric is introduced, its fitting and validation become additional parts of the procedure.

For a simple scaled fixture, query q=(0,0) and candidates a=(1,0), b=(0,2), c=(1,1) have squared distances 1,4,2. Top-2 selects a and c. Sorting squared distances gives the same ordering as sorting Euclidean distances, so taking square roots is unnecessary for exact neighbor selection.

Exclude an anchor by record ID before selection. Removing only the first neighbor assumes the anchor is uniquely first, which can fail under ties. Removing every zero-distance row discards distinct duplicate records that may be legitimate evidence. Stable tie handling and identity-based exclusion make the policy explicit.

At deployment, filter by eligibility before taking top-k. A nearby row with an unavailable label cannot serve as labeled context. Taking k neighbors first and then dropping illegal ones can leave a smaller, differently distributed context than retrieving k from the eligible pool.

Model architecture: retrieval around an actual pretrained PFN¶

The inference path is training-fitted preprocessing → query-to-memory distances → eligible neighbor IDs → labeled local context plus unlabeled query → pretrained row-token PFN → class probabilities. For the fine-tuned arm, local training episodes update the PFN before the same retrieval inference path is evaluated. The query label appears only in the episode loss or final scoring, never inside its context input.

Our measured local experiment uses the historical v1 checkpoint, 32-neighbor contexts and six gradient steps, with three seeds on three small tasks. Only 24 fixed test rows per task are scored to keep exact-neighbor inference affordable. This deliberately small sample makes uncertainty very weak. It is a real pretrained adaptation experiment, not a reproduction of LoCalPFN's full results. The no-preprocessing gradient path, small budgets and feature geometry are named deviations.

Approximate neighborhoods to share work¶

If every query uses a different exact neighborhood, the PFN cannot share one context computation across the whole query batch. Retrieval lookup may be cheap while the many forward and backward passes become expensive. The paper's episode construction trades some neighborhood accuracy for shared computation.

Sample an anchor from training data. Retrieve enough nearby rows for a context and several queries, excluding the anchor. Shuffle that neighborhood, then split it into disjoint context and query subsets. All those queries share the context, so one forward pass can train them together. Neighbors of an anchor are not guaranteed to be each other's nearest neighbors; that is the approximation, not a bug. Section 2.4.

Your code must retain the context and query IDs for every episode and assert disjointness. The known query targets supervise the loss after prediction. In the author run, validation selects among adaptation steps; the test set evaluates only the selected state. A nonzero parameter-change check confirms that the adapted arm really updated weights. It does not establish that the update was beneficial.

Shared episodes trade exact locality for reusable computation¶

Exact query-specific neighborhoods can require a separate PFN context computation for every query. Retrieval lookup may be cheap relative to repeatedly running the model. To share work during adaptation, sample an anchor, retrieve a larger neighborhood around it and divide that neighborhood into context and query subsets.

The anchor is excluded from the retrieved set. The context and query subsets must have disjoint IDs. Query labels supervise the episode loss after the forward pass; they must not appear among the context labels used for those predictions.

Being near the same anchor does not imply being each other's nearest neighbors. In one dimension, an anchor at 0 can have nearby points at −1 and +1; those points are distance 2 apart. The shared-context episode approximates per-query local neighborhoods to reduce repeated computation. That approximation is part of the method's cost/quality trade-off.

Shuffling the retrieved neighborhood before splitting prevents a deterministic near/far ordering from always assigning the closest records to one role. Preserve the random seed and resulting IDs so an episode can be replayed exactly. The split should be validated before model execution.

An optimizer step updates pretrained parameters using the query loss. A nonzero parameter delta demonstrates that adaptation occurred. It does not demonstrate that the adaptation improved generalization. Save episode losses, validation scores and the selected step, then evaluate the selected state on untouched test rows.

Selection includes how long to adapt¶

Zero steps is a meaningful candidate: the frozen retrieved-context model. If validation favors it, the experiment should be allowed to conclude that local adaptation was not useful under this budget. Forcing the final step into the report can hide harmful adaptation.

Context reuse can dominate nearest-neighbor lookup cost¶

Suppose preparing a PFN context costs a units and predicting one query against prepared context costs b units. For Q queries sharing one context, a simplified total is a+Qb. If every query has a unique neighborhood requiring fresh preparation, it becomes Q(a+b). When a is large, the second can be much more expensive even if retrieving neighbor IDs is fast.

Grouping nearby queries around shared anchors aims to recover some reuse. It changes the contexts, so the quality/cost trade-off must be measured. A faster approximate neighborhood is useful only if its predictive consequences are acceptable for the intended workload.

Cache keys need to include everything that determines the prepared state: context identities and labels, preprocessing/feature order, checkpoint identity and relevant inference settings. Fine-tuning changes weights and can invalidate caches built before adaptation. Reusing stale context states can silently compare inconsistent predictors.

In the local report, separate neighbor-search time from PFN context preparation and query prediction where the implementation exposes them. This helps identify whether a future optimization should target retrieval, batching or the model's inference path. A faster nearest-neighbor library may have little effect if repeated context computation dominates.

Compare failures as carefully as gains¶

The global and local frozen arms share the same checkpoint and feature treatment. The adapted local arm starts from a copy of those original weights. Copying matters because some historical packages cache model instances globally: mutating one instance can silently change what you thought was the untouched baseline.

A retrieved context can contain only one class. The local runner then uses a declared constant prediction for that context instead of manufacturing missing-class examples from the test set. This boundary should be visible in a production context policy. Expanding k until all classes appear would be another valid, but different, train-label-informed retrieval rule.

Measured interpretation. Exact retrieval alone does not uniformly improve the global v1 baseline. Six-step local fine-tuning changes the actual pretrained parameters and has the best mean rank in this three-task, 24-test-row-per-task panel. The small test sample and conditional seeds make this exploratory; no broad adaptation superiority follows.

A neighborhood can lose a class the global task requires¶

If the retrieved labels contain only one class, the underlying classifier API may reject the context or produce a restricted class schema. The local runner uses a declared constant prediction policy for this case. This keeps the result defined without inventing examples from held-out data.

Another possible policy expands k until enough classes are represented, using only eligible training labels. That is a different retrieval procedure with a different cost and information distribution. It should be compared explicitly rather than silently added only to rescue failed queries.

Report how often the fallback occurs and which queries it affects. An average loss can conceal a small subset of catastrophic failures. Coverage and probability validity are part of the prediction contract, especially when context selection varies by query.

The local adaptation panel is deliberately small: a few tasks, few gradient steps and only a small fixed test sample per task. It can show actual checkpoint updates and exploratory paired outcomes. It cannot resolve broad superiority or reproduce a large benchmark through a favorable rank alone.

Translate the mechanism into a relational hypothesis¶

A relational neighborhood can replace Euclidean proximity with connections through entities and events. The same questions survive: which rows are eligible, what labels are available, how identities are excluded and which context computations can be shared. A graph edge is not automatically evidence that a neighbor is useful or legal.

A graph retrieval mechanism earns credit only after those information and budget boundaries are checked.
